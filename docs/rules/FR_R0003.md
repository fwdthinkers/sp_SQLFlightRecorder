# FR_R0003 TopWaitTypeSpike

| Field | Value |
|---|---|
| RuleId | `FR_R0003_TopWaitTypeSpike` |
| Category | Waits |
| Severity | Medium — **escalates High** on critical wait types (see below) |
| Confidence | Medium |
| Evidence type | Inferred |
| Introduced in | 0.1 (escalation completed in 0.4.3) |
| Lifecycle | Active |
| Data source | `FR_Wait`, `FR_Snapshot` |
| Dedup anchor | 60-second bucket (per-window single top wait; D-074) |

## What it detects
The single wait type with the largest **increase** in cumulative wait time
across the report window — i.e., the wait the instance spent the most *new* time
on during the incident.

## How it is computed
Repository-only (D-081). For the first snapshot at or after `@DeltaStartUtc`
(the window start, or the first post-restart snapshot when a restart split the
window — D-064) and the last snapshot in the window, the rule computes
`DeltaWaitMs = last.WaitTimeMs − first.WaitTimeMs` per wait type and takes the
single largest positive delta. Wait types on the collect-time ignore list
(`WaitStatsIgnoreList`, D-033/D-057) never reach `FR_Wait`, so they cannot be
selected. Cumulative counters that reset on restart cannot produce a false spike
because the delta anchors post-restart (D-064).

## Severity rationale
Base **Medium** (a wait increase is a signal, not a confirmed problem). It
**escalates to High** when the top wait type is one of the six hard-coded
critical wait types (D-093): `PAGEIOLATCH_*`, `WRITELOG`, `RESOURCE_SEMAPHORE`,
`LCK_M_*`, `THREADPOOL`, `SOS_SCHEDULER_YIELD`. These are the conservative
community-consensus "these waits hurt" set. Escalation is by wait **class**, not
by row count, so it does not violate D-069; the `FR_Rules` catalog severity
stays the Medium base (D-091). The rule uses the hard-coded list, **not** the
`CriticalWaitTypes` config key (whose honoring is deferred to v1.1, D-105).

## Confidence rationale
**Medium.** A cumulative-wait delta is a real observation but does not by itself
attribute cause (the wait could be a symptom of blocking, IO, or memory), hence
not High.

## Evidence-type rationale
**Inferred** — the elevated wait is consistent with pressure but the rule does
not observe the root cause.

## False-positive risks
- A benign workload shift (e.g., a nightly batch) can raise a wait without an
  incident. The non-critical case stays Medium precisely to avoid over-alarming.
- A very short window with one busy moment can make a small absolute delta "top".

## False-negative risks
- Sub-minute spikes are invisible at the default 1-minute cadence (D-042).
- If the spiking wait is on `WaitStatsIgnoreList`, it is filtered at collect time
  and never considered.
- Only the single largest delta is reported; a secondary critical wait is not.

## Drill-down guidance
Correlate the wait type with the window's blocking (`FR_R0001`/`FR_R0007`), IO
(`FR_R0004`), and memory (`FR_R0005`/`FR_R0024`) findings before acting. For
`PAGEIOLATCH_*` look at file latency; for `RESOURCE_SEMAPHORE`/`THREADPOOL` look
at memory grants and worker pressure. Do not act on the wait name alone.

## Suppress / disable
```sql
EXEC dbo.sp_SQLFlightRecorder @Mode = N'Configure',
    @ConfigKey = N'DisabledRules', @ConfigValue = N'FR_R0003_TopWaitTypeSpike';
```
Disabled rules are listed in the FR_R0026 coverage summary (D-101).

## Related config keys
- `WaitStatsIgnoreList` — wait types excluded at collect time (D-033/D-057).
- `CriticalWaitTypes` — defined but **not yet honored**; escalation uses the
  hard-coded D-093 list until v1.1 (D-105).

## Example
```sql
-- Seed a THREADPOOL spike across two snapshots, then report (see tests/rules/).
-- FR_R0003 fires at High because THREADPOOL is a critical wait type.
EXEC dbo.sp_SQLFlightRecorder @Mode = N'Report', @OutputFormat = N'FindingsOnly';
```
See [tests/rules/run-rule-fixtures.sh](../../tests/rules/run-rule-fixtures.sh)
for the positive (critical→High), positive (non-critical→Medium), and negative
(no delta→silent) fixtures.
